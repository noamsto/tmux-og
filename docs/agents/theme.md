# Theme (light/dark)

The `tmux-client-theme` and `og-remote-theme` rows in `scripts.md` carry the script-level detail.

- **Theme support**: tmux state (`@catppuccin_flavor`/`@thm_*`) and Catppuccin Latte/Mocha colors accordingly, driven by two independent signals now. An external `theme-toggle` run is the only writer of `$XDG_STATE_HOME/theme-state.json`, and also drives tmux via its own `update_tmux`. A terminal theme report (tmux's `client-*-theme` hooks → `tmux-client-theme`, #663) converges tmux state alone — `@catppuccin_flavor`/`@thm_*` — and **never** touches `theme-state.json`; that file is `theme-toggle`'s alone, and once a server is up it is read only as a **cold-start seed** for `@catppuccin_flavor` when the option is still empty at config load (see `generator/render/base.go`'s `pluginConfigs`), never again afterward. **Renderer consistency**: because a terminal report can now diverge tmux state from the file, every in-repo reader prefers the LIVE tmux flavor when running under tmux, falling back to the state file only outside tmux or before `@catppuccin_flavor` is set — `lib-claude.sh`'s `setup_claude_colors` (optional pre-expanded-flavor argument, else one `show-options` fork when `$TMUX` is set, else the file), and the Go `themestate.Detect()` call sites (`picker/statusline`'s `--flavor` CLI flag, `picker/tui.go`/`picker/whichkey.go`'s `readTmuxOpts()`-derived `@catppuccin_flavor`, `picker/splash`'s own `show-options` fork) — none of them modify the external `themestate` module itself, they adapt only at the call site. The flavor is server-global, so with several attached clients the last one to attach or change theme holds. Control-mode clients (the remote bridge) have no tty and never fire the hooks, so a bridge attach cannot flip the theme; a terminal that never answers DSR 996 never fires either. An ssh-attached client's report is ignored while any other attached client is local (non-ssh, non-control); an all-ssh/headless server's reports are followed — see the `tmux-client-theme` row in `scripts.md`. A terminal pinned opposite the desktop would revert the desktop on every attach — `set -g @og_follow_client_theme off` disables the handler at runtime. Design: `docs/superpowers/specs/2026-09-16-client-theme-hooks-design.md`.
- **Reload race (#871)**: one desktop toggle runs `theme-toggle`'s `update_tmux` in parallel with kitty re-theming (`_run_updates_parallel`), and kitty's theme report fires the hook, so two reloads used to overlap. Each clears `@thm_*` (`set -ogq` never overwrites), and a command client's `source-file` reads every nested file through the client (async round trips, other clients' commands run in the gaps), so a clear landing mid-catppuccin makes `set -gF message-style "fg=#{@thm_teal}…"` fail `invalid style` and `catppuccin.tmux` exit 1 (measured 5/10 on a scratch server; tmux-fingers' hint styles fail the same way). The `'…' returned 1` line went to the hook job's stdout, and a `run-shell -b` job with no `-t` prints into view mode on the reporting client's active pane — a mirror's renderer pane when that client is on a mirror session. Now the hook waits out a running `theme-toggle` (`theme-apply-macos` on macOS; executable match only, see `scripts.md`), so the flow does one reload, its output never reaches a pane, and its no-op guard needs a loaded palette — so a palette that never loads reloads on every report (bounded by the lock and the nonconverged break). The residual (a hook job already applying when `theme-toggle` starts) needs `theme-toggle` to take `${TMPDIR:-/tmp}/og-client-theme-$UID.lock` (nix-config); `prefix + r` still reports its own errors in view mode by tmux design. Spec: `docs/superpowers/specs/2026-09-29-theme-reload-race-design.md`.
